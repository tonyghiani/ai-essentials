# Brainstorm

Widen first, narrow second, and never both at once. The pool is generated by agents that cannot see each other, judged only against criteria fixed before any idea existed, and stress-tested before the user picks.

Two findings shape every step. Agents that debate converge on one idea and lose the rest, so lens agents never see each other's output. And a model asked for one answer gives the most typical one, so every lens returns several ideas with a probability each, and the low-probability tail is kept on purpose.

Paths below are relative to **this skill's own directory**. If a read fails, `ls` the skill directory rather than guessing.

## Where sessions live

Outside any repo, in one folder the user can open from anywhere:

```
${AI_BRAINSTORMS_DIR:-$HOME/brainstorms}/
  INDEX.md                         one line per session, newest first
  <YYYY-MM-DD>-<slug>/
    session.md                     frame, criteria, option map, ranking, pre-mortems, log
    pool.md                        every raw idea, with lens and probability
    adr.md                         the decision (feature and architecture modes)
    synthesis.md                   the map of positions (topic mode)
    research.md                    web-research output, when the frame needed outside facts
```

`INDEX.md` lines look like `- 2026-10-30 · open · [Websocket fan-out for alerts](2026-10-30-websocket-fan-out/session.md) · repo: owner/name`. Status is `open`, `decided` or `parked`. Create the folder and the index on first use.

Write `session.md` as you go, phase by phase, so a session interrupted halfway resumes from the file. On "resume the brainstorm on X", find it in `INDEX.md`, read `session.md`, say which phase it stopped in, and continue.

## Modes

| Mode | When | Lens set | Ends with |
|---|---|---|---|
| `feature` | What to build for users | Feature defaults in `lenses.md` | `adr.md` |
| `architecture` | How to build or restructure a system | Architecture defaults | `adr.md` |
| `topic` | Anything else: a strategy, a talk, a process, a question to understand | Topic defaults | `synthesis.md` |

Pick the mode from the request and say which one you picked; the user corrects it in one word if wrong.

**Quick mode.** For a small question ("three ways to name this flag"), skip the fan-out: generate 8 ideas inline with probabilities, cluster, recommend, and write only `session.md`. Offer quick mode when the question fits in one sentence and nothing is hard to undo.

## Phase 1: Frame (with the user)

Inside a repo, read the code the topic touches before asking anything the code can answer. When the frame depends on outside facts (what a library supports, how others solved it), run the `web-research` skill in quick depth and save it as `research.md`.

Then ask, numbered, each with your recommended answer:

1. **Problem**: one sentence, as "How might we ...". Restate theirs; don't accept a solution disguised as a problem.
2. **Constraints**: what is fixed (stack, deadline, team, budget, compatibility).
3. **Non-goals**: what this session will not solve.
4. **Criteria**: 3–5, with a weight each (high, medium, low). Fix them now: criteria written after the ideas get tailored to the favourite. Defaults to offer: user value, cost to build, cost to run and operate, reversibility, risk.
5. **Already tried or ruled out**, and why.
6. **Your own ideas**: ask for them now, before the pool exists, so they aren't anchored by the agents' ideas. "None" is a fine answer.

Write the frame and criteria to `session.md`. Move on when the user confirms, or answers and says go.

## Phase 2: Diverge (fan-out, no judging)

Pick 4–6 lenses from `lenses.md` for the mode. Always include the baseline lens and one subtractive lens; the rest come from the defaults, swapped for others when the frame suggests (an on-call-heavy system gets the operator lens). Say which lenses you picked.

Launch one agent per lens **in parallel**, each in a fresh context. Each brief carries only:

- the frame and constraints from `session.md` (not the criteria: generators that know the scoring optimise for it)
- that lens's paragraph from `lenses.md`
- in a repo, the repo root and the paths worth reading, with a read-only constraint
- the output block below, verbatim

Never include the user's ideas, your own leaning or another lens's output.

```
Return exactly 5 ideas. For each:

### <short title>
- pitch: one sentence
- how: up to three lines on how it works
- cost: what it takes to build and to run
- risk: the most likely way it goes wrong
- p: the probability (0.00–1.00) that a typical senior engineer given this frame would propose it

At least two ideas must have p below 0.10. Do not rank or recommend. Do not drop an idea for looking infeasible.
```

In Claude Code: one message, one Agent call per lens, `effort: "lower"`, `model: "sonnet"`. Elsewhere, parallel workers if available, else sequentially in this chat.

Append every idea to `pool.md` with its lens and `p`, plus the user's own ideas tagged `[user]`.

## Phase 3: Cluster (with the user)

Merge duplicates and near-duplicates into 6–12 distinct options. Each option gets an id (`O1`…), a title, a two-line description and the lenses it came from. Keep the strongest low-`p` ideas as options even when they look odd: they are why the fan-out exists. A combination of two ideas is a new option, not a merge.

Show the map to the user as a short list grouped by theme. Ask, numbered: kill any, add any, combine any? No scores and no favourites yet. Write the final map to `session.md`.

## Phase 4: Converge (blind ranking)

Rank with two fresh agents, so neither you nor the lens agents grade your own work:

1. Strip lens names, `p` values and `[user]` tags. Relabel the options `A`, `B`, `C`… in a shuffled order, and keep the mapping in `session.md`.
2. Ranker 1 gets the options in that order; ranker 2 gets them reversed. Both get the frame and the weighted criteria, and nothing else.
3. Each returns, per criterion, the options in order best to worst with a one-line reason for the top and bottom, then an overall top 3.
4. Finalists are options in both rankers' top 3. When that leaves fewer than two, add the next best by combined position. Where the rankers disagree sharply, show it: the disagreement says the criteria are ambiguous.

Standard-tier model, `effort: "lower"`, in parallel. Map the letters back before showing the user.

## Phase 5: Pre-mortem (finalists only)

One agent per finalist, in parallel, fresh context, read-only in a repo:

```
It is six months after this option shipped and it failed. Write the most likely story of how, in five
sentences, grounded in the frame and, in a repo, in the code you read. Then:
- door: one-way or two-way, and what backing out would cost
- early signal: the first observable sign it is going wrong
- cheapest test: the smallest experiment that would raise or kill confidence before committing
```

Use the strongest available model here (the session model in Claude Code); a shallow pre-mortem is worse than none.

## Phase 6: Decide (the user decides)

Show a comparison of the finalists: criteria as rows, finalists as columns, one word per cell, and each pre-mortem's story and door underneath. Give your recommendation and why, in two sentences. The user picks, combines or sends it back to Phase 2 with a changed frame.

Then:

1. **feature / architecture**: write `adr.md` from `adr-template.md`. Every option in the final map appears under "Options considered", each with a fair, specific reason it lost; a strawman makes the ADR useless later.
   **topic**: write `synthesis.md`: the positions, where they disagree and why, what would settle each disagreement, and what to read next.
2. Set the session to `decided` (or `parked`) in `INDEX.md`.
3. Offer, numbered, with recommendations:
   - **Record it** as a precedent, when future work in this repo should follow it: `ai-decisions add --class design --situation "<s>" --decision "<d>" --why "<w>" --scope <repo-key> --record <path to adr.md>`. Skip for one-off choices.
   - **Grill it**: run `grill-me` on the chosen option to reach a spec. Recommend this for any one-way door.
   - **Share it**: when the tool can publish a page (an Artifact in Claude Code), publish the option map, comparison and pre-mortems for the team. Offer in one line; don't publish unasked.

No code, scaffolding or branch until the user says to build. Building is the `tech-lead` or `deliver` skill's job, starting from the ADR.

## Cost

A full session is about 10–14 agent runs: 4–6 lenses and 2 rankers on the cheap tier, 2–3 pre-mortems on the strong one. Quick mode is none. Say the count before the fan-out when the user hasn't asked for a full session.

## Gotchas

- One sentence of your own opinion in a lens brief, and every lens returns variations of it. Brief from `session.md`, not from memory of the conversation.
- Lens agents told the criteria return ideas shaped to score well and the pool narrows. Criteria go to the rankers only.
- Don't let lens agents see each other's output or "build on" it. That is the debate pattern, and it collapses the pool.
- A `p` of 0.02 on an idea that is plainly the default means the lens ignored the instruction. Re-run that lens once; if it repeats, drop its probabilities from the cluster step.
- Clustering is where tail ideas die quietly. Before showing the map, check at least two options trace back to ideas with `p` below 0.10.
- The user's own idea gets no special treatment in ranking. It is blind like the rest; that is the point of stripping tags.
